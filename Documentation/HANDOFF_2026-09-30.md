## 3. Audit findings (read-only; nothing fixed yet) — SECURITY AND REVENUE

Not verifiable from repos: live Supabase RLS/grants/bucket settings, the `debit_minutes`/`credit_minutes` SQL, VPS env file, live nginx config, xAI price.

### A. Transcription API auth
- **A1 Critical — `POST /transcribe`** (main.py ~151-172): unauthenticated even if `API_KEY` were set; accepts 25 MB files (nginx `client_max_body_size 25m`), runs sync transcription inside the API process (512 MB cap), blocks the event loop → credit burn / DoS. The iOS app never calls it (`RenderTranscriptionService.transcribe` has no callers) → safe to disable. **Quick mitigation without a deploy: block it in nginx.**
- **A2 Critical — `POST /jobs`** (main.py ~21-36, 90-125): `API_KEY` unset ⇒ allow all; `user_id` taken from body. Any caller with a valid user UUID can queue jobs; `audio_url` arbitrary and `provider` selectable. Worker fetch (jobs.py ~182-201) uses `follow_redirects=True`, no host allowlist, no size cap ⇒ **SSRF** against the box and an OOM path. No per-user limit/rate limit/quota. Chunked jobs: `get_audio_chunks(meeting_id)` (supabase_client.py ~258-289) does not filter by user ⇒ a leaked meeting_id lets an attacker transcribe/read another user's chunks with the service key.
- **A3 High — `GET /jobs/{id}`** (main.py ~128-148): no ownership check; returns transcript, summary, `audio_url`, `user_id`. IDs are `gen_random_uuid()` (capability leak, not enumeration). 500s echo DB errors.
- **A4 High (unverified) — storage/RLS:** iOS builds `.../storage/v1/object/public/recordings/<uid>/<mid>.m4a` and the worker downloads without credentials ⇒ `recordings` bucket almost certainly **public**. `audio_chunks` migration 001 never enables RLS. `transcription_jobs` RLS (supabase/migrations/20251003:40-65) lets an authenticated user INSERT/UPDATE own rows with no column limits, and the worker polls the **table**, so a signed-in user can insert/re-queue jobs via PostgREST — a JWT check in the API alone is not enough.
- **A5 Medium:** CORS `*`; nginx has no `limit_req`; both services run as root with the service key (uvicorn binds only 127.0.0.1:8100 — good).

**Fix sketch**
1. `auth.py` with `AUTH_MODE=off|log|enforce`; verify bearer via Supabase `GET {SUPABASE_URL}/auth/v1/user` (headers `Authorization: Bearer <jwt>`, `apikey: <anon>`), ~60 s cache (same approach as `openai-proxy`'s `auth.getUser`). Legacy clients send no JWT → in `log` mode allow and count.
2. `POST /jobs`: `user_id = jwt uid or body.user_id`; 403 on mismatch when JWT present; require a matching `recordings` row (regular) / `audio_chunks` rows (chunked) for (user_id, meeting_id) — works for old clients since upload always precedes job creation; per-user cap on pending/processing jobs; cap duration and chunk count.
3. `GET /jobs/{id}`: 404 unless `job.user_id == uid` (enforce); in legacy mode null out `audio_url` (Swift field optional) but keep `user_id` (non-optional in iOS decoding).
4. Delete or 410 `/transcribe`.
5. Worker: download via service-key storage with path regex `^<job.user_id>/...`; `follow_redirects=False`; size cap; filter chunks by `user_id`; then make `recordings` bucket private (playback already uses signed URLs, `SupabaseManager.swift` ~113).
6. RLS: revoke INSERT/UPDATE on `transcription_jobs` from `authenticated` or `WITH CHECK (status='pending')`; nginx `limit_req` on `POST /jobs`; drop CORS.
7. iOS (`RenderTranscriptionService.swift` ~47/106/165): add `Authorization: Bearer <SupabaseManager.shared.client.auth.session.accessToken>` to the 3 requests (as `OpenAIService` does); treat 401 as non-retryable; remove `transcribe()`.
8. Rollout: ship iOS build → `AUTH_MODE=log`, count legacy requests → `enforce` after adoption (pair with a force-update prompt; enforcing early makes old builds' polls fail silently).

### B. Minutes accounting — server-side jobs are NEVER debited (bug)
- Client only checks `currentBalance >= ceil(min)` (CreateMeetingView ~1602-1616); `trackMeetingCreated(transcribed:false)` is stats only. `applyJobStatusUpdate .completed` has no debit. Python never writes minutes. `debit_minutes` is called only from on-device paths (CreateMeetingView ~1425, ~2020; MeetingDetailView ~1439; LocalTranscriptionJobManager ~461), keyed by `p_meeting_id`, `auth.uid()`-based so the worker cannot call it.
- Consequence: unlimited server-side hours as long as balance ≥ one file's length; many concurrent long files against one balance; free tier never depletes on long files.
- Fallback (MeetingDetailView ~1682-1729) triggers on 3 client **polling** failures, not on job failure; runs on-device and debits once while the server job may still complete and cost money (result discarded) ⇒ users charged when VPS is flaky, not when it works.
- Client quirk: `isDuplicateDebitError` (MinutesManager ~535) treats any error containing "constraint"/"already" as success ⇒ a balance-check violation could be free usage.
- Worker duration is `len(bytes)/32000` (wrong, ~4× low for 64 kbps AAC); the xAI branch now measures with ffprobe for regular jobs; chunked jobs use client-supplied duration.
- Revenue: OpenAI ≈ $0.27/audio hour (plus LLM pennies); forgone minutes worth roughly €0.22–0.63/hour.
- **Fix:** after the worker saves results, call a service-only RPC keyed by `meeting_id` (same key as the client debit so fallback + worker can't both charge); reject `POST /jobs` with 402 when balance < `ceil(duration/60)`; periodic sweep for completed jobs with `minutes_debited IS NULL`; iOS: mark debited when a job completes and fire the fallback only after the job is confirmed failed. Ledger table/column names in the agent's SQL sketch (`debit_minutes_for_job`, `minutes_ledger`) are **placeholders** — the real ledger SQL is not in the repos; read it from Supabase first. Record provider on the ledger for cost analytics.

**Recommended order:** (1) block/disable `/transcribe`, worker URL/path validation + size cap + no redirects, tighten `transcription_jobs` RLS, filter chunks by user; (2) server-side debit + create-time balance check; (3) JWT `log` mode → iOS header → `enforce`; (4) nginx rate limits, non-root services, private bucket; (5) fallback double-work fix and duration measurement.

## 4. Plans (researched, not implemented on the iOS side)

### Background upload ("close the app right after starting")
Findings: today `CreateMeetingView.processServerSide` (~1602-1777) uploads in-process with a `beginBackgroundTask` (~30 s), via supabase-swift foreground uploads that load whole files into RAM (`SupabaseManager.uploadAudioChunk` ~153-218, `uploadAudioRecording` ~29-91), then `POST /jobs`; worker polls `pending` every 20 s. UI copy "Keep SnipNote open while uploading" at `MeetingDetailView` ~305/323.
Design (server half is being built on `claude/background-upload-backend`):
1. `POST /jobs` with `upload_pending=true` creates job status `awaiting_upload`, mints a Supabase **signed upload URL**, returns `{job_id, upload_url, ...}`; idempotent per `meeting_id`; requires the Supabase JWT.
2. iOS: `URLSessionConfiguration.background(withIdentifier:)`, `sessionSendsLaunchEvents = true`, `uploadTask(with:fromFile:)` raw PUT to the signed URL (no async/await completions; delegate only), file copied first to a stable folder (Application Support/PendingUploads), `handleEventsForBackgroundURLSession` in `AppDelegate` (`SnipNoteApp.swift` ~181), tasks matched by `taskDescription = meetingId`. No upload chunking in this path (single original file).
3. Worker `promote_uploaded_jobs()` flips `awaiting_upload` → `pending` when the object exists with the expected size; TTL sweep fails stale ones.
4. App-level reconcile on launch (today results are only applied when `MeetingDetailView` polls).
5. Keep the 3-retry + on-device fallback semantic, but see audit B for the fallback flaw.
**Hard limit to communicate in UX:** swipe-away (force-quit) cancels background session tasks on iOS (from Apple docs/knowledge, not device-verified). User can leave/lock the phone but must not swipe the app away until upload finishes; resume on next launch.
**Unverified:** Supabase accepting a raw-body PUT to a signed URL (supabase-js uses multipart); bucket file-size limit must allow ~150 MB; TUS resumable is a poor fit (every piece needs app code).
**Worker blocker:** non-chunked path decodes whole files with pydub (2 h ≈ 1 GB+ PCM vs `MemoryMax=1500M`, `MAX_CONCURRENT_JOBS=1`) — xAI branch fixes it for xAI; the background-upload branch addresses OpenAI with streamed download + `ffmpeg -f segment`.
Effort estimate: iOS 3-4 days, VPS 2-3, testing 1.

### Live Activity / Dynamic Island
Findings: no widget extension and no ActivityKit code exist. Targets: SnipNote, SnipNoteTests, SnipNoteUITests, **SnipNoteShare** (a share extension already exists — it's for imports; it cannot start Live Activities). `SnipNote.entitlements` has only the app group `group.com.mattianalytics.snipnote`; no `aps-environment`, no `NSSupportsLiveActivities`, no `registerForRemoteNotifications`. Processing UI is `MinimalistProcessingView.swift` (big 72 pt percentage, 3 pt `MinimalistProgressBar`, phases only `uploading/transcribing/analyzing`; the "uploading" state is really `status == .pending && progress == 0`, i.e. queue wait, not upload — `MeetingDetailView` ~301). Completed/failed notifications are sent by the app itself in `applyJobStatusUpdate` (~1201-1228) ⇒ **they don't fire when the app is closed** (existing bug).
Recommendation: local Live Activity + redesigned stage view first (Upload → Transcribe → Summarize → Done, determinate bar only during transcription, drop the big percentage, add Done/Failed + haptic, copy "You can close the app. We'll notify you."), then **remote updates via APNs** from the worker (`pushType: .token`, per-activity token stored in Supabase, `apns-push-type: liveactivity`, `apns-topic: <bundle>.push-type.liveactivity`, final `event: end` with alert). Don't ship the local-only version alone — it freezes once the app is suspended.
Manual requirements: add the Widget Extension target in Xcode (widget extension target can't be hand-written safely), Push Notifications capability, regenerate provisioning, `NSSupportsLiveActivities = YES` in the **app** Info.plist, APNs auth key (.p8) + Key ID + Team ID in VPS env. Needs a real device. Users can disable Live Activities in Settings — UI must work without them. `content-state` JSON keys must match the Swift `ContentState` Codable keys exactly. Server half is on `claude/apns-live-activity-backend` (incl. `docs/LIVE_ACTIVITY_CONTRACT.md`). iOS half (LiveActivityManager, widget, stage view, token upload) is **not started** — do it after merging the iOS branches above because it touches `MeetingDetailView`/`MinimalistProcessingView`/`CreateMeetingView`.

## 5. Speaker labels (researched, NOT started — waiting on owner's yes)

Sources were search results (docs hosts were blocked from the sandbox) — verify against official docs before building.
- **xAI:** `POST /v1/stt`, `diarize=true`, model `grok-voice-transcribe-2.0` ⇒ `words[]` with text/start/end/integer `speaker`, up to 20 speakers; ~500 MB per file (unverified); diarization included in the price (~$0.10/h ⇒ ≈ $0.0017/min, ~63% cheaper than today's OpenAI $0.0045/min); one request ⇒ consistent speaker IDs across the whole file (follows from the design, not explicitly documented).
- **OpenAI:** only `gpt-4o-transcribe-diarize` (`response_format=diarized_json`, `chunking_strategy="auto"`, 25 MB limit, labels only valid within one request, optional known-speaker references). **Deprecated 2026-08-26, removed 2027-02-26**; `gpt-transcribe` (used today) does **not** diarize. Dead end.
- **Recommendation:** diarization **only on xAI**, built on the single-request path (`claude/xai-single-request`). Data model: `transcription_jobs.segments jsonb` `[{speaker,start,end,text}]` (group consecutive same-speaker words), keep `transcript` plain/“Speaker 1: …” for search and summary prompts; iOS `Meeting` gets `transcriptSegmentsData: Data?` + `speakerNamesJSON: [String:String]` (rename map resolved at render/export time); extend `JobStatusResponse`; speaker-labelled transcript view + rename UI; export renderers already print speaker labels. Effort ≈ 1–1.5 weeks. Risks: Italian/overlapping-speech accuracy untested; privacy policy must name xAI as a processor; long-file timeouts.
